01一页概览

系统由三块组成：一个浏览器页面、一个 Node 进程、以及三个外部服务。页面不持有任何账号密钥，所有需要密钥的操作都在 Node 进程完成。房间返回的「想做什么」只是意图，能不能真正打到设备上由本地闸门决定。

三条设计主线

  • 密钥边界：BRTC_AK、BRTC_SK、BRTC_LICKEY 只存在于 Node 进程。浏览器拿到的是本次通话的进房 token、房间名和 uid。
  • 意图与执行分离：模型在房间里说「打开夜灯」不算执行。动作要经 src/frames.mjs 收成结构化 action，再经 src/policy.mjs 四道检查，放行后才打 IoT。
  • 回合可作废：每句输入领取一个回合代号。用户说下一句时，上一句还在路上的字幕、播报和卡片全部按代号丢弃，不会串到新对话里。
当前形态

这是一个可运行的技术验证骨架，不是生产系统。设备控制主线已经跑通真实 UAT，但 HTTP 接口本身没有鉴权，存储是本地 JSON 文件，多实例部署还不成立。详见 15 已知限制。

02系统定位与边界

需求说明书要求把助手嵌进箭牌智家 App。当前这一版先做 WebView 可承载的独立 H5，把业务能力跑通，集成形态留给后续评审。

本版做什么

能力实现方式状态
设备控制语音或文字 → 意图解析 → 安全闸门 → 箭牌 IoT已跑通
场景创建create_scene 意图 → POST /ext/v3/ai/scene链路在，未联调
产品百科问句送进房间，由控制台知识库作答依赖平台

App 原生集成SDK 封装、登录态传递均未做未开始

明确不做的事

  • 不创建售后工单。报修只提供跳转入口，工单闭环留在 App 侧。
  • 不落地知识库文件。切片、向量检索、回答边界全部由百度控制台的知识库意图承担，仓库内没有检索代码。
  • 不保存用户身份。页面没有登录体系，审计里的操作人恒为 app-user。
  • 不接管 BRTC 自身的语音能力。ASR、TTS、大模型全部由房间侧完成，本服务只处理文字帧。

03总体架构

浏览器与 Node 服务之间有两条边，浏览器与 BRTC 之间还有一条不经过本服务的直连边。后者是音频流和字幕帧的通路，也是这条架构里最容易被忽略的部分：语音并不流经我们的服务。

部署拓扑

当前是单进程单实例，没有反向代理、没有 TLS、没有数据库。Node 进程同时承担 HTTP 服务、会话状态、闸门判定和审计落盘；IOT_MODE=mock 时还会在 127.0.0.1:18901 起一个本地模拟网关。

05建连与授权激活

官方 H5 示例把 AK/SK 放在浏览器里直接调 generateAIAgentCall。本实现改成服务端建实例，页面只拿进房参数。授权是网关主动推来的，页面把原文交回服务端，由服务端拼激活帧。

为什么要固定 devId

后端按 licenseKey + appId + deviceId 计一次激活。每次换 BRTC_DEVID 都会算作一台新设备，持续消耗授权额度。.env.example 里把它写成固定值 DEVID-ARROW-H5-0001，就是为了这个。

签名细节

BCE v3 签名要求 host 与 content-type 显式参与签名，否则网关卡在 Signature does not match。签名有效期 1800 秒。示例网关 ai.agent.kaywang.cn 不认这个 AppID，会回 No such app，所以走正式域名 rtc-aiagent.baidubce.com。

人设位置

建实例时不传 sceneRoleCfg。人设由百度控制台绑定到该 AppID 的自定义角色提供，避免每次建实例把它覆盖掉。建实例时只带语音相关参数：中文、热词表、按键长语音模式、开场白文本。

06一轮对话

一轮对话的数据流分两段：浏览器到 Node（HTTP），Node 到房间（数据通道）。语音输入多一步本机 ASR 收尾，但最终都汇到同一个 sendText 分流函数。

语音输入时序

时刻动作延时
按下麦克风打开房间麦克风—
按下后发送 [E]:[CMD]:[ASR_START_LONGTEXT_REC]200 ms
按住期间房间回 [Q]:[M] 中间态，逐字更新同一条用户气泡流式
松开发送 ASR_STOP_LONGTEXT_REC立即
松开后关闭房间麦克风600 ms
松开后等最终 [Q]，超时则提示「没听清」8000 ms
按住上限到点自动结束录音55 s

先开麦再开识别，是为了避免房间录到一段静音。停识别后等 600 ms 再关麦，是为了不截掉尾音。

sendText 的四个分支

页面拿到一句话后按固定顺序做正则分流，命中即停。这个顺序决定了报修不会被设备指令抢先接走。

顺序匹配去向是否进房间
1数据统计话题POST /api/topic → 适配层否
2报修 / 维修本地渲染报修卡 + deeplink否
3设备操作动词POST /api/intent → 本地指令解析否
4其余全部POST /api/turn 领代号，再发 [T]:原话是
README 与实现不一致

README 描述「设备清单附在操作类 [T] 后面」。当前代码里 sayToRoom() 只发 [T]:原话，并没有请求 GET /api/roster 拼清单。buildRole() 与 /api/roster 仍然可用，是留给房间侧人设或后续接线的；过滤侧（服务端 visibleReply、页面 userEcho）完整保留，用来处理房间回放整段 [T] 的情况。

房间回答的处理

房间的流式片段以 [A]:[M] 到达，页面累加到 agentBuf 并在同一条气泡上改字。最终帧是整句而不是增量，所以收到最终帧时不能再往已累积的片段后面接。最终帧交给 POST /api/frame，服务端从中摘出动作、过闸，再把过滤后的正文和卡片返回页面。

房间自己的 TTS 会念一遍回答。为了不让同一句话念两遍，页面把已经通过 [E]:[CMD]:[TEXT]: 播报过的文本记进 spokenLocal 集合，房间把它作为 [A] 回放时直接丢弃。

07指令的三条入口

设备动作可以从三条完全不同的路径进来，最后都收敛到 turn.finish()。这是这套架构里最容易看错的部分：本地已经处理过的指令，房间可能还会再问一次。

入口 A · 本地意图

POST /api/intent。页面正则命中设备动词后直接调用，不经过房间。服务端按原话补全 cmd、param、value，再按房间与品类收窄设备。

入口 B · 函数调用

[F] 帧。控制台配好 control_device、create_scene、open_repair 三个意图后由模型发起。

入口 C · 回答内代码块

最终 [A] 里带 ```iot 块或裸 JSON。意图没配好时的兜底路径，extractAction() 摘出来并从正文删掉。

↓ 三条入口统一收成 action 对象 ↓

turn.finish() 补全 → 消歧 → policy.evaluate()

↓

allow

立即打 IoT，追加审计，出执行卡。

不执行。挂 5 分钟待确认单，页面出确认卡。

直接拒绝，给出原因，不出执行卡。

重复指令的抑制

本地意图（入口 A）处理完后，房间在几秒内通常还会发起一次 control_device。页面记下 localIntentAt，60 秒内收到同名函数调用时不走闸门，直接回一个不播报的函数结果，内容明确告诉模型「已由页面列出设备，请用户点选，不要再追问」。没有这一步，模型会因为「没拿到函数结果」反复追问设备。

多设备消歧

模型给的 deviceName 只信设备清单里存在的值。trustedName() 校验不过就丢掉，改由用户原话重新匹配：先看房间（主卫 / 客卫），再看品类（马桶 / 浴缸 / 镜柜），最后看指令能力。命中一台直接下发，命中多台出选择卡，一台都没有则明确说不下发。

08安全闸门

闸门是整套系统里唯一决定「能不能下发」的地方。模型只表达想做什么，闸门负责说不。所有检查在 src/policy.mjs 内，不依赖网络。

confirmAtOrAbove 设为 H，denyAtOrAbove 设为 C。也就是高危要确认，严重级直接拒绝。目前没有规则会产出 C 级，拒绝实际只发生在校验失败时，等级记为 X。

待确认动作的生命周期

PENDING ──claim()──▶ EXECUTING ──settle()──▶ SUCCEEDED / FAILED
   │
   ├──reject()──▶ REJECTED          // 用户点取消
   └──超 5 分钟──▶ EXPIRED           // claim 时惰性判定

claim() 把状态从 PENDING 改成 EXECUTING 并返回记录。重复调用会拿到「动作已是 EXECUTING」，所以双击确认按钮也只会下发一次。超时判定写在 claim() 里，是惰性的，没有后台定时器。

审计留痕

每条下发都写一行 audit.jsonl，字段覆盖需求 3.4 要求的三项：操作人、时间、设备与动作，另外把闸门判定和 IoT 往返也记下来，便于追溯。

字段内容
at actor sessionId时间、操作人、会话号
kind homeId targets动作类型、家庭号、逐台设备与指令
level reasons decision风险等级、判定理由、EXECUTED 或其他
iotRequest iotResponse完整往返，鉴权头经 redact() 脱敏

平台返回 HTTP 200 只代表接口可达。业务是否成功看 body 里的 code 与 success：code 为 200 或 10000 且 success !== false 才算成功。

09回合编排与打断

用户可以在助手还在回答时说下一句。如果不做处理，上一句迟到的字幕会盖到新对话上。系统用「回合代号」解决这个问题，服务端和页面各持一份。

两份发号器

位置载体作用
服务端session.turnGenPOST /api/turn 自增并返回。带旧代号返回的 /api/frame、/api/intent 请求，结果标记为 superseded
页面createTurnGate()维护 turnGen、claimTicket、turnBusy、turnKind 与待发队列，决定哪个结果还能上屏

页面状态机的四条规则

  • 领代号即打断：openTurn() 先发 [B] 停掉上一句的 TTS，再向编排层领新代号。
  • 领号竞态只留最后一句：claimTicket 自增，回来时票号对不上就作废，只保留最后一次领取。
  • 过期结果不上屏：stale(gen) 在 turnOpening 为真或代号不等时返回真，页面直接丢弃返回值。
  • 房间超时自释放：房间发出后 20 秒没有最终回复，这一轮自行结束，队列里的下一句接着发。

打断时的保留与丢弃

对象处理
上一句的流式字幕丢弃，按代号判断
上一句的 TTS 播报发 [B] 停止，并暂停页面内所有音视频元素
已经画出的设备选择卡保留在页面上，用户仍可点选
服务端已放行的指令继续执行并写审计，只是结果不再交给页面

最后一条是刻意的选择：一旦指令过了闸门，就当成已发生的事实，不因为用户说了下一句而回滚。代价是可能出现「用户没看到结果但设备已经动了」，换成语音播报反馈能缓解。

10数据与存储

没有数据库。三份本地文件，全部同步 IO，由 src/store.mjs 统一封装。

文件格式内容增长

内存态与磁盘态的分界

会话的完整记录只在内存 Map 里，进程重启即丢。写进 state.json 的只有 id、title、lic、instanceId、createdAt、closedAt 六个字段。所以重启之后会话列表还在，但拿它发帧会被拒。

为什么卡片要单独存

闸门卡、执行结果卡、设备选择卡都不是 BRTC 字幕的一部分，房间回放时拿不回来。要还原一次对话的界面状态，只能靠 cards.jsonl。同理，制动两张卡的 pendingId 只存在于内存，重启后旧的确认卡点了会报「待确认动作不存在」。

13前端架构

三个视图共用一个页面，没有构建工具、没有框架、没有依赖包。app.js 是一个 ES module，直接由浏览器加载。

视图与导航

视图内容数据来源
通话对话流、快捷句、输入框、按住说话BRTC 字幕 + /api/*
家庭设备按房间分组的设备与在线状态GET /api/devices?fresh=1
安全审计最近 80 条操作流水GET /api/audit

对话区气泡的状态变量

变量语义
userBubble当前正在写入的用户气泡，带 data-live / data-pending / data-local 标记
agentBubble当前助手气泡，流式片段在它上面累加
agentBuf已累积的流式片段，最终帧到达时清空
sentText本地已画出的用户原话，用来对上房间回放的 [Q]
lastAsk本轮提问，用于过滤模型复读与清单照抄
spokenLocal已本地播报过的文本，房间回放同一句时丢弃
localIntentAt上次本地意图时间，60 秒内抑制重复的 [F]

移动端适配

  • 760px 以下换成上栏布局，标志在左，通话 / 设备 / 审计在右。
  • 输入字号固定 16px，避免 iOS 聚焦时放大页面。
  • 按住说话用 setPointerCapture，手指移出按钮再松开也会正常结束录音。
  • 键盘弹出时用 visualViewport 算出遮挡高度，把输入栏平移到键盘上方。
  • 非安全上下文（http）直接提示「浏览器不允许使用麦克风」。麦克风必须走 https。

质检页面

public/accept.html 在浏览器里跑一遍过滤逻辑的一致性校验，把页面的 visibleReply / userEcho 与服务端 src/roster.mjs 的同名函数逐条比对。两边实现是分开写的，这个页面用来防止它们漂开。

15已知限制

按对上线的影响排序。阻塞 表示不修不能上生产，待补 表示影响完整度，已知 表示可以暂缓。

项影响级别
HTTP 接口无鉴权任何人可下发设备指令、读全部审计阻塞
无 TLS 与反向代理麦克风在 http 下不可用，必须 https 域名阻塞
会话状态只在内存重启即丢，无法横向扩容阻塞
审计同步写文件appendFileSync 阻塞事件循环，并发上不去阻塞
离线设备不拦截指令照发，事后记 FAILED，不满足需求 3.4待补
场景创建未联调链路在，没有一次端到端验证待补
场景删除不支持不可逆操作的二次确认无从验证待补
用户身份缺失审计操作人恒为 app-user，无跨用户隔离待补
设备清单注入未接线模型只能靠人设猜设备名，消歧靠原话补救待补
chosenOnce 只增不减长期运行内存缓慢增长已知
无 HTTP 层集成测试路由、序列化、错误分支没有自动化覆盖已知

并发能力

需求要求每分钟不低于 20 路会话。当前架构下，闸门与解析是纯内存计算，瓶颈在审计落盘（同步写）和会话状态（单进程）。单实例跑 20 路应该能撑住，但没有测过，也没有连接数保护。
